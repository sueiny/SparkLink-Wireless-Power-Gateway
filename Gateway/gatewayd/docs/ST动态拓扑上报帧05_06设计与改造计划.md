# ST 动态拓扑上报帧 05/06 设计与改造计划

> Status: Historical design and migration plan.
> Authority: 背景、改造拆分和历史设计细节可参考本文；最终 ST 协议不以本文为准。
> Superseded by: [ST帧对接规定.md](ST帧对接规定.md).
> Last verified against: `gatewayd/config/gateway_config.json` on 2026-06-28 for inventory counts only.

本文定义新增 ST 帧类型 `0x05` 和 `0x06` 的文本 payload 规则，并作为后续实现计划。root 固件和网关侧实现的最终对接规则以 `ST帧对接规定.md` 为准。

强约束：`gatewayd` 与 root 的对接层只使用三种 ST 帧类型：

| frame_type | 名称 | 用途 |
| ---: | --- | --- |
| `0x02` | `DATA` | 上行 Modbus 业务数据、下行控制业务数据。 |
| `0x05` | `DTU_NETWORK_TOPOLOGY` | root 上报完整 DTU 网络拓扑文本。 |
| `0x06` | `EXTERNAL_DEVICE_MAP` | root 上报 DTU 与外接设备映射文本。 |

`HEARTBEAT(0x01)`、`TOPO_SUMMARY(0x03)`、`DEPTH_UPDATE(0x04)` 只属于 DTU SLE Tree 内部协议或旧版说明，不作为后续 gateway-root 主链路对接帧。

## 1. 背景和目标

当前目标模式下，`gatewayd` 通过 `gateway_config.json` 预先知道全量设备 inventory 和数量：有多少 DTU、多少外接设备、外接设备的 `type/product_id/modbus_type/modbus_addr`。运行期拓扑和在线状态只来自 root 最新有效 `0x05/0x06` 快照。

`devices[]` 和 DTU 配置条目在 `topology.source=root_report` 下只作为 inventory 和白名单，不作为静态拓扑关系使用。只有 `topology.source=static_json && static_json.enable_for_test=true` 时，JSON 静态拓扑才作为内部测试输入。

旧版 ST `TOPO_SUMMARY(0x03)` 只表达“某个节点的直连子节点列表”，不适合一次上报完整 DTU 树，也不携带外接设备清单。后续 gateway-root 对接不再依赖 `0x03`。

新增目标：

- `0x05 DTU_NETWORK_TOPOLOGY`：root 上报完整 DTU 网络拓扑文本。
- `0x06 EXTERNAL_DEVICE_MAP`：root 上报“DTU 节点 -> 外接设备”键值对文本。
- `gatewayd` 可通过配置选择：
  - 正式模式：读取 JSON inventory，等待 root 上报 `0x05/0x06` 后判断在线和挂载关系。
  - 内部测试模式：显式切换 `static_json` 后读取 JSON 静态拓扑。

职责边界保持不变：

- `gatewayd` 负责协议解析、拓扑建模、物模型映射、Modbus/ST 业务处理。
- `sle_data_app` 只负责 SLE 连接管理、上行 IPC 转发、下行 raw ST 转发，不解析 `0x05/0x06` 文本。

## 2. ST 帧类型扩展

公共 ST 帧头保持 13 字节不变：

```text
magic(2) version(1) frame_type(1) src_role(1)
src_node_id(2 LE) dst_node_id(2 LE) seq(2 LE)
payload_len(2 LE) payload(N)
```

新增帧类型：

| frame_type | 名称 | 方向 | payload | 用途 |
| ---: | --- | --- | --- | --- |
| `0x02` | `DATA` | 双向 | `modbus_rtu` | 唯一业务数据帧。 |
| `0x05` | `DTU_NETWORK_TOPOLOGY` | root -> gatewayd | UTF-8/ASCII 文本 | 完整 DTU 树拓扑快照。 |
| `0x06` | `EXTERNAL_DEVICE_MAP` | root -> gatewayd | UTF-8/ASCII 文本 | 外接设备挂载关系。 |

通用约束：

- `dst_node_id` 应为 `0`，表示上报给 gateway。
- `src_node_id` 是上报 root 的节点 ID。
- `payload_len` 最大受 `SLE_FRAME_MAX_PAYLOAD=1011` 限制。
- 如果完整文本超过 1011 字节，必须定义分片方案后再落地；当前版本仍使用 ASCII-hex 文本上报，不引入二进制分片。
- 文本换行统一解析为 `\n`；接收端需要兼容 `\r\n`。
- 空行忽略。

## 3. `0x05` DTU 网络拓扑文本

`0x05` payload 使用当前调试输出风格的树形文本，每行一个 DTU 节点。缩进和连接符表达父子关系。

示例：

```text
1
|- 36
|  |- 39
|  |  |- 38
|  |  |- 48
|  |  |  |- 32
|  |  |  |- 47
|  |  |  |- 54
|  |  |  |- 57
|  |  |  `- 68
|  |  `- 63
|  `- 42
|     |- 43
|     |  |- 34
|     |  `- 61
|     `- 58
|        |- 50
|        `- 52
|- 37
|  |- 23
|  |- 27
|  |  |- 59
|  |  `- 60
|  `- 46
|     `- 45
|- 41
|  |- 33
|  |  `- 26
|  |- 35
|  |  `- 31
|  `- 67
|     |- 53
|     |- 56
|     `- 69
|- 44
|  |- 22
|  |  |- 55
|  |  |- 62
|  |  `- 65
|  |- 24
|  |  |- 28
|  |  |- 49
|  |  |- 51
|  |  `- 66
|  `- 25
`- 64
   `- 40
      `- 30
```

### 3.1 解析规则

每行解析出：

- `node_id`：行尾数字。
- `depth`：根据连接符前的树形缩进计算。
- `parent_id`：最近一个 `depth - 1` 的节点。
- `child_ids`：由解析出的父子关系反向聚合。

第一行没有连接符时认为是 root：

```text
1
```

带连接符的行允许两种连接符：

```text
|- 36
`- 64
```

解析端应忽略连接符和竖线，只保留数字节点 ID。建议第一版严格要求每个节点 ID 为 `1..65535` 的十进制整数。

### 3.2 生成的内部拓扑

示例片段：

```text
1
|- 36
|  |- 39
|  |  |- 38
```

应生成：

| node_id | parent_id | child_ids |
| ---: | ---: | --- |
| `1` | `0` | `36` |
| `36` | `1` | `39` |
| `39` | `36` | `38` |
| `38` | `39` | 空 |

`0x05` 是完整拓扑快照。解析成功后应替换该 root 对应的旧动态路由，不再复用 `0x03 TOPO_SUMMARY` 的局部 owner 更新语义。

### 3.3 错误处理

以下情况应拒绝整帧，并保留旧拓扑：

- 没有 root 行。
- 同一 payload 内 node_id 重复。
- 出现无法识别的非空行。
- 第一行 depth 非 0。
- 某行 depth 跳级，例如从 depth 0 直接到 depth 2。
- node_id 超出合法范围。
- payload root 与 ST 头 `src_node_id` 不一致。
- 出现 JSON DTU inventory 未登记的 `node_id`。
- 不同 root 最新快照聚合后出现重复 DTU 节点。

日志建议：

```text
[SLE-TOPO][05] parsed root=1 nodes=48 source=dynamic
[SLE-TOPO][05][ERROR] duplicate node_id=36 line=...
```

## 4. `0x06` 外接设备映射文本

`0x06` payload 每行一个键值对，表示某个 DTU 节点下挂一个外接设备。只有拥有外接设备的 DTU 才出现在 payload 中；未出现的 DTU 表示只有节点本体，没有外接设备。

示例：

```text
DTU_001-RELAY_001
DTU_002-ENV_001
DTU_004-METER_001
```

### 4.1 解析规则

每行格式：

```text
DTU_<node_id>-<external_device_id>
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `DTU_<node_id>` | `DTU_` 前缀 + 十进制节点 ID，允许 `DTU_001` 这种三位补零格式。 |
| `external_device_id` | 必须存在于 `gateway_config.json` 外设 inventory，后续可扩展更多设备 ID。 |
| 分隔符 | 固定 `-`。 |

示例解析结果：

| 文本行 | dtu_id | device_id | 元数据来源 |
| --- | ---: | --- | --- |
| `DTU_001-RELAY_001` | `1` | `RELAY_001` | JSON 外设 inventory |
| `DTU_002-ENV_001` | `2` | `ENV_001` | JSON 外设 inventory |
| `DTU_004-METER_001` | `4` | `METER_001` | JSON 外设 inventory |

`0x06` 不推断设备类型，也不携带 `modbus_type/modbus_addr`。这些元数据固定来自 JSON inventory。若现场需要同一设备动态修改地址，后续应扩展 JSON 配置或 06 文本格式。

### 4.2 错误处理

以下情况应拒绝整帧，并保留旧映射：

- `DTU_` 节点 ID 无法解析。
- 外接设备 ID 未登记在 JSON 外设 inventory。
- DTU 未登记在 JSON DTU inventory。
- 同一外接设备 ID 在同一个 payload 或不同 root 最新快照聚合后重复出现。
- 聚合后外设数量超过 `expected_external_device_count`。

允许情况：

- 同一 DTU 在同一个 `0x06` payload 中出现多次，表示该 DTU 挂载多个外接设备。
- `0x06` 可以映射到当前 `0x05` 中未在线的 DTU；该帧仍有效，但对应外设在线状态为 `online=0 reason=parent_dtu_offline`。

日志建议：

```text
[SLE-TOPO][06] parsed external_devices=3 root=1 source=dynamic
[SLE-TOPO][06][ERROR] unknown device prefix device_id=FOO_001
```

## 5. 配置接口计划

新增配置段已经放入 `gateway_config.json`：

```json
"topology": {
  "source": "root_report",
  "expected_dtu_count": 69,
  "expected_external_device_count": 9,
    "online_policy": {
      "dtu_from_topology_snapshot": true,
      "external_from_device_map": true,
      "external_inherits_dtu_online": true,
      "emit_online_change": true,
      "missing_dtu_online": false,
      "missing_external_online": false
  },
  "static_json": {
    "enable_for_test": false
  },
  "dynamic": {
    "required_frames": ["dtu_topology", "external_map"],
    "startup_timeout_ms": 30000,
    "persist_path": "/userdata/gateway/data/dynamic_topology.json",
    "allow_fallback_to_static": false
  }
}
```

字段含义：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `topology.source` | `root_report` | 正式模式等待 root 上报 `0x05/0x06`；`static_json` 只用于内部测试。 |
| `expected_dtu_count` | 当前为 `69` | 期望 DTU 总数；JSON DTU inventory 数量必须等于该值。 |
| `expected_external_device_count` | 当前为 `9` | 期望外接设备总数；JSON 外设 inventory 数量必须等于该值。 |
| `online_policy.dtu_from_topology_snapshot` | `true` | DTU 在线状态来自当前聚合 `0x05` 快照。 |
| `online_policy.external_from_device_map` | `true` | 外接设备在线状态来自当前聚合 `0x06` 映射。 |
| `external_inherits_dtu_online` | `true` | 外接设备必须挂载在当前 05 在线 DTU 上才在线。 |
| `emit_online_change` | `true` | 快照引起在线状态变化时发布对应遥测。 |
| `missing_dtu_online` | `false` | JSON inventory 中存在但当前 05 缺失的 DTU 判定离线。 |
| `missing_external_online` | `false` | JSON inventory 中存在但当前 06 缺失的外设判定离线。 |
| `static_json.enable_for_test` | `false` | 只有内部测试允许设为 true 并切换 `source=static_json`。 |
| `required_frames` | `["dtu_topology", "external_map"]` | 动态拓扑认为 ready 所需帧。 |
| `startup_timeout_ms` | `30000` | 预留字段；当前在线判定不做 root 上报超时推断。 |
| `persist_path` | `/userdata/gateway/data/dynamic_topology.json` | 动态拓扑解析成功后的持久化路径。 |
| `allow_fallback_to_static` | `false` | 正式模式不回退静态 JSON，避免把测试拓扑误当真实拓扑。 |

静态 JSON 内部测试模式必须显式开启：

```json
"topology": {
  "source": "static_json",
  "static_json": {
    "enable_for_test": true
  }
}
```

## 6. 在线判定规则

正式 `root_report` 模式下，在线状态完全由最新有效快照决定：

| 对象 | 在线条件 | 离线原因 |
| --- | --- | --- |
| DTU | 出现在所有 root 最新有效 `0x05` 聚合拓扑中 | `snapshot_missing` |
| 外接设备 | 出现在所有 root 最新有效 `0x06` 聚合映射中，且对应 DTU 在当前 05 聚合拓扑中在线 | `snapshot_missing` 或 `parent_dtu_offline` |

关键约束：

- `DATA(0x02)` 只承载业务遥测或控制，不改变 DTU 或外接设备在线状态。
- 停止某个外接设备 DATA，但 05/06 仍存在时，该外接设备保持在线。
- root 长时间不继续上报时，gatewayd 保持上一份有效快照状态，不自行根据时间判定离线。
- 若 root 要表达设备离线，必须在下一份完整 `0x05/0x06` 快照中移除该 DTU 或外设映射。
- 进入规则引擎、AI、MQTT 前，gatewayd 会按 `device_id` 合并同一发布窗口内的遥测，后到字段覆盖先到字段，避免 05/06/DATA 同批重复扩大设备数。

## 7. 持久化格式计划

`0x05/0x06` 解析成功后，后续可保存为 JSON 文件，避免重启后必须立刻等待 root 重报。当前首版在线判断以内存中的最新有效快照为准。

示例：

```json
{
  "version": 1,
  "source": "root_report",
  "root_id": 1,
  "updated_at_ms": 1710000000000,
  "dtu_nodes": [
    {"node_id": 1, "parent_id": 0, "child_ids": [36, 37, 41, 44, 64]},
    {"node_id": 36, "parent_id": 1, "child_ids": [39, 42]}
  ],
  "external_devices": [
    {
      "device_id": "RELAY_001",
      "type": "relay_device",
      "product_id": "relay_device",
      "dtu_id": 1,
      "modbus_type": 4,
      "modbus_addr": 1
    }
  ]
}
```

## 8. 实施状态

### P0 文档和测试样例

- 更新 `DTU_SLE_TREE数据帧格式.md`，登记 `0x05/0x06`。
- 更新 `上下行测试包格式与用例.md`，补充 `0x05/0x06` 文本 payload 示例。
- `dtu_root_run_sender.py topology-all` 已用于 PC 侧模拟最终效果：先发 `0x05/0x06`，再发 `0x02 DATA`。

### 已完成 gatewayd 解析和配置

- `config_manager` 增加 `TopologyConfig`。
- `gateway_config.json` 增加 `topology.expected_dtu_count` 和 `topology.expected_external_device_count`，作为所有 root 快照聚合后的完整性判断基准。
- `sle_frame_parser` 增加帧类型常量：
  - `SLE_FRAME_TYPE_DTU_NETWORK_TOPOLOGY = 5`
  - `SLE_FRAME_TYPE_EXTERNAL_DEVICE_MAP = 6`
- 新增 `gateway::datasource` 下的文本解析能力：
  - `parseDtuTreeText(payload)`
  - `parseExternalDeviceMapText(payload)`
- `SleDataSource::collect()` 识别 `0x05/0x06`，解析成功后更新运行期拓扑状态。
- `SleDataSource::collect()` 对 `0x01/0x03/0x04` 在 gateway-root 对接模式下忽略并记录告警，避免旧帧继续影响主拓扑。
- 当前正式模式不回退静态 JSON：未收到 `0x06` 映射前，`DATA` 找不到外设时直接丢弃，不自动生成 DTU 遥测。
- 解析成功后写入 `persist_path` 待后续实现。

### 后续运行期设备模型整合

- 动态外设由 `0x06` 生成运行期 `DeviceInfo`。
- ThingsKit 子设备上线通知、遥测 publish、离线规则、AI 窗口、命令路由统一使用动态设备表。
- 下行控制查 root 时优先用动态 `RouteTable`。
- 处理动态拓扑变更：
  - 新增节点上线。
  - 节点消失离线。
  - 外设迁移到其他 DTU。

### 板端联调

- root 启动后先发 `0x05` 完整 DTU 树，再发 `0x06` 外设映射。
- root 后续普通采集和下行控制只使用 `0x02 DATA`。
- gatewayd 日志验收：
  - `[SLE-TOPO][05] parsed root=... nodes=...`
  - `[SLE-TOPO][06] parsed external_devices=...`
  - `topology_source=dynamic`
- 之后发送普通 `DATA(0x02)`，确认设备 ID 映射来自 `0x06`。
- 断电重启后验证 `persist_path` 可恢复动态拓扑。

## 9. 关键风险

- `0x05` 文本受 1011 字节 payload 上限约束。当前两路 root 按各自子树上报，69 个 DTU 可通过多 root 聚合；如果单 root 子树继续增大并超过 1011 字节，需要新增分片或压缩规则。
- 文本缩进解析对格式敏感。需要 root 输出固定格式，避免不同终端宽度或字符导致解析歧义。
- `0x06` 当前只表达 `DTU -> device_id`，没有表达 `modbus_addr`、设备型号、额定电流等参数；现场完整配置仍可能需要 JSON 或扩展语法补充。
- 动态拓扑如果直接替换 `devices[]`，会影响 ThingsKit 子设备关系、规则引擎、AI 特征窗口和命令下行路由，必须作为独立阶段验证。

## 10. 推荐首版策略

首版实现建议采用保守策略：

- 默认 `topology.source=root_report`，正式链路等待 `0x05/0x06`。
- `source=static_json` 仅内部测试使用，且必须显式设置 `static_json.enable_for_test=true`。
- 增加日志和 dry-run 测试，先确认 root 文本格式稳定。
- 确认格式稳定后，再把 `0x05/0x06` 解析结果用于在线/离线判定和下行路由。
