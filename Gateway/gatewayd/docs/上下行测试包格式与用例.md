# 上下行测试包格式与用例

> Status: Current test reference with historical records.
> Authority: 真实 SLE 联调测试包、COM/ADB 命令和验收结论以本文为入口；协议字段以 [ST帧对接规定.md](ST帧对接规定.md) 为准。
> Superseded by: None.
> Last verified against: `gatewayd/config/gateway_config.json` and `sle_data_app/test/dtu_root_run_sender.py` on 2026-06-28.

本文记录当前 Gateway 真实 SLE 联调使用的上行、下行测试包格式和验收用例。协议封装职责固定在 `gatewayd`：物模型、Modbus RTU 和 ST DATA 帧都由 `gatewayd` 构造；`sle_data_app` 只管理 SLE 连接，并把 IPC 收到的 raw ST 原样写入 root。

后续 gateway-root 对接层强制只使用三种 ST 帧：`DATA(0x02)`、`DTU_NETWORK_TOPOLOGY(0x05)`、`EXTERNAL_DEVICE_MAP(0x06)`。`HEARTBEAT(0x01)`、`TOPO_SUMMARY(0x03)`、`DEPTH_UPDATE(0x04)` 不再作为 gateway-root 主链路输入。完整规定见 `ST帧对接规定.md`。

## 1. 总体链路

上行链路：

```text
Windows COM 脚本
  -> DTU root UART
  -> SLE notify
  -> sle_data_app notify_printer
  -> gatewayd SLE data IPC
  -> Modbus 解析
  -> ThingsKit MQTT/SQLite
```

下行链路：

```text
ThingsKit/本地测试命令
  -> gatewayd command
  -> root_report 模式下查询 0x06 外设映射和 0x05 DTU root
  -> gatewayd 构造 Modbus RTU
  -> gatewayd 构造完整 ST DATA
  -> sle_data_app raw ST forward
  -> SLE write root
  -> DTU root COM 打印或业务处理
```

## 2. 设备拓扑来源

正式模式下，`gatewayd` 的设备拓扑来自 root 上报：`0x05` 上报 DTU 拓扑，`0x06` 上报外接设备映射。`gateway_config.json` 的 `topology.expected_dtu_count` 和 `topology.expected_external_device_count` 提供全网总量基准，用于判断所有 root 最新快照聚合后是否完整。

配置来源：

| 配置段 | 内容 | 当前用途 |
| --- | --- | --- |
| `sle` | `enable/data_socket/cmd_socket` | 只配置 SLE IPC 开关和两个 socket；当前配置没有 `sle.roots`。 |
| `topology` | 拓扑来源、期望 DTU 数量、期望外设数量、在线判定策略 | 正式模式使用 `source=root_report`。 |
| `devices[]` | 外接设备和 DTU inventory | 正式模式作为全量名单、数量校验和外设 `type/modbus_type/modbus_addr` 白名单；不保存静态挂载关系或静态父子关系。 |

静态表只在内部测试模式使用：

```json
"topology": {
  "source": "static_json",
  "static_json": {
    "enable_for_test": true
  }
}
```

上行 DATA 帧进入 `gatewayd` 后，映射逻辑为：

```text
ST header src_node_id
  -> 作为 dtu_id
  -> topology.source=root_report 时优先查 0x06 动态外设映射
  -> 找到则按外接设备 device_id/type 上报
  -> 找不到则丢弃该 DATA 或按当前实现记录原因
  -> topology.source=static_json 且 enable_for_test=true 时才使用 JSON 静态拓扑字段
```

正式 `root_report` 配置中，外接设备条目不允许填写 `dtu_id/dtu_node_id`，DTU 条目不允许填写 `parent_id/child_ids`。这些字段只允许在 `static_json` 内部测试模式中表达静态拓扑。

正式模式下，外接设备与物模型的绑定由 `0x06 EXTERNAL_DEVICE_MAP` 决定：

| 字段 | 说明 |
| --- | --- |
| `DTU_<node_id>` | 挂载外接设备的 DTU 节点 ID，也是上行 ST `src_node_id` 的匹配键。 |
| `external_device_id` | 必须存在于 JSON 外设 inventory。 |
| `type/product_id` | 从 JSON 外设 inventory 读取，不从 ID 前缀推断。 |
| `modbus_type/modbus_addr` | 从 JSON 外设 inventory 读取；`0x06` 只提供挂载关系。 |

正式动态拓扑模式下，新增外接设备仍需要先进入 JSON inventory；运行时挂在哪个 DTU、是否在线由 root 上报 `0x05` 完整 DTU 拓扑和 `0x06` 外接设备映射决定。静态 JSON 拓扑只保留内部测试用途。

正式配置示例：

```json
{
  "device_id": "RELAY_001",
  "product_id": "relay_device",
  "name": "RELAY_001",
  "type": "relay_device",
  "station_id": 1,
  "modbus_addr": 1,
  "modbus_type": 4
},
{
  "device_id": "DTU_010",
  "type": "dtu_node",
  "node_id": 10
}
```

在线判定固定如下：

| 对象 | 在线条件 | DATA 影响 |
| --- | --- | --- |
| DTU | 出现在所有 root 最新有效 `0x05` 聚合拓扑中。 | DATA 不影响 DTU 在线。 |
| 外接设备 | 出现在所有 root 最新有效 `0x06` 聚合映射中，且对应 DTU 在当前 05 聚合拓扑中在线。 | DATA 不影响外设在线。 |

外接设备离线原因：

| reason | 含义 |
| --- | --- |
| `snapshot_missing` | JSON inventory 中有设备，但当前 06 聚合映射没有该设备。 |
| `parent_dtu_offline` | 06 中有设备映射，但对应 DTU 不在当前 05 在线拓扑中。 |
| `snapshot_present` | 06 中有设备映射且对应 DTU 在线。 |

异常帧处理：

- 05 上报未知 DTU、root 与 ST 头 `src_node_id` 不一致、跨 root 重复 DTU，拒绝本帧。
- 06 上报未知外设、未知 DTU、重复外设，拒绝本帧。
- 05/06 聚合数量超过 `expected_*_count`，拒绝导致超量的本帧。
- root 长时间不重新上报时，gatewayd 保持上一份有效快照状态，不做超时离线。

## 3. ST 帧完整格式

当前 ST 帧头长度固定为 13 字节，小端字段如下：

| 偏移 | 长度 | 字段 | 示例 | 说明 |
| --- | ---: | --- | --- | --- |
| 0 | 2 | magic | `53 54` | ASCII `ST` |
| 2 | 1 | version | `01` | 当前版本 |
| 3 | 1 | frame_type | `02` | gateway-root 主链路只允许 `02/05/06` |
| 4 | 1 | src_role | `01`/`04` | root 上行为 `01`，gateway 下行为 `04` |
| 5 | 2 | src_node_id | `01 00` / `00 00` | 上行 root 为 1，下行 gateway 为 0 |
| 7 | 2 | dst_node_id | `00 00` / `09 00` | 上行发 gateway 为 0；下行发目标 DTU |
| 9 | 2 | seq | `2A 00` | 测试序号 |
| 11 | 2 | payload_len | `0A 00` | payload 字节数 |
| 13 | N | payload | 见下文 | `modbus_rtu` |

完整 ST 帧：

```text
ST_FRAME = ST_HEADER(13B) + PAYLOAD(payload_len)
```

限制：

| 项 | 值 | 说明 |
| --- | ---: | --- |
| `SLE_FRAME_HEADER_LEN` | 13 | 固定帧头长度。 |
| `SLE_FRAME_MAX_LEN` | 1024 | 当前 gatewayd/sle_data_app 支持的最大 ST 帧长。 |
| `SLE_FRAME_MAX_PAYLOAD` | 1011 | `1024 - 13`。 |

帧类型：

| frame_type | 名称 | payload | gateway-root 对接约束 |
| ---: | --- | --- | --- |
| `2` | `DATA` | `modbus_rtu` | 唯一业务数据帧；上行遥测和下行控制都使用 DATA。 |
| `5` | `DTU_NETWORK_TOPOLOGY` | 文本树 | root 上报完整 DTU 网络拓扑快照。 |
| `6` | `EXTERNAL_DEVICE_MAP` | 文本键值对 | root 上报 DTU 与外接设备挂载关系。 |

说明：`1/3/4` 可存在于 DTU Tree 内部协议或旧版测试说明中，但不属于后续 gateway-root 对接帧集合。

角色：

| role | 名称 | 说明 |
| ---: | --- | --- |
| `1` | `ROOT` | root 节点上行常用角色。 |
| `2` | `RELAY` | 中继节点。 |
| `3` | `LEAF` | 叶子节点。 |
| `4` | `GATEWAY` | gatewayd 构造下行 ST 时使用。 |

### 3.1 DATA payload

DATA payload 格式：

| 偏移 | 长度 | 字段 | 说明 |
| --- | ---: | --- | --- |
| 0 | N | modbus_rtu | 标准 Modbus RTU，末尾 CRC16-Modbus 小端 |

当前解析规则：设备归属由 ST `src_node_id` + 当前 `0x06` 映射确定，设备类型由 JSON inventory 的 `modbus_type` 决定。

| modbus_type | 设备 | 上行功能码 | 数据解释 |
| ---: | --- | --- | --- |
| `2` | 单相电表 | `0x04` | 8 个寄存器：电压、电流、有功功率、功率因数、频率、电量、继电器状态。 |
| `3` | 温湿度 | `0x03` | 2 个寄存器：湿度、温度。 |
| `4` | 继电器 | `0x01` | 线圈状态，当前取 bit0 为 `relay_state`。 |

下行 DATA 帧同样直接承载 Modbus RTU 控制帧。`gatewayd` 下行 builder 会把 ST `dst_node_id` 写为目标外设当前挂载的 DTU；root 固件负责按该目标节点自动转发。

### 3.2 `0x05/0x06` 动态拓扑 payload

`0x05 DTU_NETWORK_TOPOLOGY` payload 是完整 DTU 树文本，每行一个节点。示例片段：

```text
1
|- 36
|  |- 39
`- 64
```

`0x06 EXTERNAL_DEVICE_MAP` payload 是 DTU 与外接设备键值对，每行一个挂载关系。示例：

```text
DTU_001-RELAY_001
DTU_002-ENV_001
DTU_004-METER_001
```

完整解析规则见 `ST帧对接规定.md` 和 `ST动态拓扑上报帧05_06设计与改造计划.md`。

## 4. 上行测试包

脚本位置：

```bash
app/Gateway/sle_data_app/test/dtu_root_run_sender.py
```

Windows 执行使用 `py -3`，串口固定 115200 8N1。打开串口会导致 DTU 初始化，因此脚本先持续发送 warmup 文本，再发送 ST 帧。

单 root、`METER_001` 上行示例：

```bash
py -3 dtu_root_run_sender.py COM19 COM23 COM36 \
  --scenario meter-001 \
  --duration 60 \
  --interval 1 \
  --line-delay 0.02 \
  --warmup-sec 5 \
  --warmup-interval 0.2 \
  --warmup-text 12123213 \
  --post-warmup-delay 3 \
  --no-heartbeat
```

串口写入格式：

```text
0 <ST_FRAME_HEX>\r\n
```

`0` 表示目标 gateway 节点，`ST_FRAME_HEX` 为完整 ST DATA 帧十六进制文本。

PC 脚本模拟：

```bash
py -3 dtu_root_run_sender.py COM19 COM23 \
  --port-root COM19=1 \
  --port-root COM23=10 \
  --scenario topology-all \
  --duration 60 \
  --interval 5 \
  --line-delay 0.02 \
  --warmup-sec 5 \
  --warmup-interval 0.2 \
  --warmup-text 12123213 \
  --post-warmup-delay 3
```

`--port-root` 是 PC 测试脚本对串口的 root 分配，不来自 `gateway_config.json` 的 `sle.roots`。当前脚本默认值为 `COM19=1, COM23=10`，但内置 `topology-all` 仍按旧 `1..9/10..69` 节点生成；当前配置要求 `DTU_001..DTU_009` 使用 `node_id=101..109`，直接回放旧脚本会被 gatewayd 拒绝未知 DTU。当前配置验收前应同步脚本测试数据或使用自定义 replay/scenario。

旧脚本 `topology-all` 每轮发送：

| 顺序 | frame_type | 说明 |
| ---: | ---: | --- |
| 1 | `0x05` | COM19/root 1 的旧 DTU 拓扑快照。 |
| 2 | `0x06` | COM19/root 1 的旧外接设备映射。 |
| 3 | `0x05` | COM23/root 10 的 DTU 拓扑快照。 |
| 4 | `0x06` | COM23/root 10 的外接设备映射；当前可为空 payload。 |
| 5+ | `0x02` | 9 个外接设备的 Modbus 遥测 DATA。 |

当前配置快照验收：

- 使用和 `gateway_config.json` 一致的 node_id 回放后，`gatewayd` 应发布 69 个 DTU 和 9 个外接设备的在线遥测。
- 从 05 移除某 DTU 后，该 DTU 发布 `online=0 reason=snapshot_missing`；该 DTU 上 06 仍映射的外设发布 `online=0 reason=parent_dtu_offline`。
- 从 06 移除某外设后，该外设发布 `online=0 reason=snapshot_missing`，其 DTU 在线状态不受影响。
- 停止某外设 DATA，但 05/06 仍存在时，该外设仍保持 `online=1 reason=snapshot_present`。
- 同一 publish 窗口内 05/06/DATA 产生重复 `device_id` 时，发布前按 `device_id` 合并，日志会出现 `telemetry batch coalesced raw=... unique=...`。

旧脚本 dry-run 检查：

```bash
python3 app/Gateway/sle_data_app/test/dtu_root_run_sender.py \
  --scenario topology-all \
  --root-id 1 \
  --dry-run \
  --preview-count 1
```

`METER_001` dry-run 样例：

```text
0 53540102010100000003001500010410089C024404FE03C4138900018AD300551624
```

拆解：

| 字段 | 值 |
| --- | --- |
| ST 头 | `53 54 01 02 01 01 00 00 00 03 00 15 00` |
| payload | `01 04 10 ...` |
| modbus_rtu | `01 04 10 ... 16 24` |
| CRC | `24 16`，小端 |

注意：该 dry-run 样例的 ST `src_node_id=1` 属于旧测试数据；当前配置下 `METER_001` 若挂在 `DTU_001`，对应 DTU `node_id=101`。

上行验收日志：


通过标准：

## 5. 下行测试包

下行测试包由 `gatewayd` 构造。当前本地隔离测试可通过 ADB forward 直接连接板端 `sle_data_app` 命令 socket，发送 `CMD_METHOD_RAW_ST_DOWNLINK=100`，用于验证 raw ST 转发和 root COM 打印。

下行命令 IPC 总帧格式：

```text
IPC_PACKET = len_le(2B) + IPC_CMD_REQUEST_BODY
```

`IPC_CMD_REQUEST_BODY`：

| 偏移 | 长度 | 字段 | 说明 |
| --- | ---: | --- | --- |
| 0 | 1 | frame_type | `0x01`，命令请求。 |
| 1 | 2 | seq | 小端，gatewayd 递增，用于匹配响应。 |
| 3 | 1 | dtu_id | 日志字段；raw ST 下行实际按 `root_id` 选 SLE 连接。 |
| 4 | 1 | method | `100` 表示 `CMD_METHOD_RAW_ST_DOWNLINK`。 |
| 5 | 2 | param_len | 小端。 |
| 7 | N | param_data | 对 raw ST 为下表结构。 |

raw ST 参数格式：

| 偏移 | 长度 | 字段 | 说明 |
| --- | ---: | --- | --- |
| 0 | 2 | root_id | root 节点 ID，小端 |
| 2 | 2 | dst_node_id | ST 帧中的目标节点，小端 |
| 4 | 2 | st_frame_len | ST 帧长度，小端 |
| 6 | N | st_frame | 完整 ST DATA 帧 |

命令响应格式：

```text
IPC_RESPONSE = len_le(2B) + frame_type(1) + seq(2 LE) + result_code(1) + data_len(2 LE) + data
```

result code：

| result_code | 说明 |
| ---: | --- |
| `0` | OK |
| `1` | FAILED |
| `2` | TIMEOUT |
| `3` | UNSUPPORTED |

当前 `sle_data_app` 只处理 `CMD_METHOD_RAW_ST_DOWNLINK=100`，不解析业务命令、不构造 Modbus。非 raw ST method 会返回 unsupported。

### 5.1 Meter 拉闸

Modbus RTU：

```text
01 10 00 10 00 01 02 AA AA 5A 1F
```

含义：

| 字段 | 值 |
| --- | --- |
| slave_addr | `01` |
| function | `10`，写多个寄存器 |
| register | `0010` |
| value | `AAAA`，拉闸 |
| CRC | `1F5A`，线缆发送顺序 `5A 1F` |

完整 ST 示例：

```text
53540102040000650000000B0001100010000102AAAA5A1F
```

拆解：

| 字段 | 值 |
| --- | --- |
| ST 头 | `53 54 01 02 04 00 00 65 00 00 00 0B 00` |
| src_role/src_node_id | `04` / `0`，gateway |
| dst_node_id | `101`，目标 DTU |
| payload_len | `11` |
| payload | `01 10 00 10 00 01 02 AA AA 5A 1F` |

### 5.2 Relay 断开

Modbus RTU：

```text
01 05 00 00 00 00 CD CA
```

完整 ST 示例：

```text
535401020400006D0001700800010500000000CDCA
```

含义：

| 字段 | 值 |
| --- | --- |
| function | `05`，写单线圈 |
| coil | `0000`，默认 channel 0 |
| value | `0000`，断开 |
| CRC | `CACD`，线缆发送顺序 `CD CA` |

### 5.3 Relay 闭合

Modbus RTU：

```text
01 05 00 00 FF 00 8C 3A
```

完整 ST 示例：

```text
535401020400006D000270080001050000FF008C3A
```

含义：

| 字段 | 值 |
| --- | --- |
| function | `05`，写单线圈 |
| coil | `0000`，默认 channel 0 |
| value | `FF00`，闭合 |
| CRC | `3A8C`，线缆发送顺序 `8C 3A` |

## 6. 下行验证命令

监听 COM 下行：

```bash
py -3 dtu_downlink_command_tester.py COM19 COM23 COM36 \
  --expect relay-open \
  --expect-dtu-id 9 \
  --channel 0 \
  --duration 60
```

或在发送上行的同时监听下行：

```bash
py -3 dtu_root_run_sender.py COM19 COM23 COM36 \
  --scenario meter-001 \
  --duration 20 \
  --interval 1 \
  --line-delay 0.02 \
  --warmup-sec 5 \
  --warmup-interval 0.2 \
  --warmup-text 12123213 \
  --post-warmup-delay 3 \
  --hold-open 40 \
  --no-heartbeat \
  --expect-downlink relay-open \
  --expect-dtu-id 9 \
  --expect-channel 0 \
  --stop-on-downlink-match
```

发送 raw ST 到板端命令 socket：

```bash
adb forward tcp:19001 localabstract:/var/run/gateway/sle_cmd.sock
python3 - <<'PY'
import socket, struct
st = bytes.fromhex("535401020400006D0001700800010500000000CDCA")
param = struct.pack("<HHH", 101, 109, len(st)) + st
body = bytes([1]) + struct.pack("<H", 1) + bytes([1, 100]) + struct.pack("<H", len(param)) + param
packet = struct.pack("<H", len(body)) + body
s = socket.create_connection(("127.0.0.1", 19001), timeout=5)
s.sendall(packet)
hdr = s.recv(2)
ln = hdr[0] | (hdr[1] << 8)
resp = b""
while len(resp) < ln:
    resp += s.recv(ln - len(resp))
print(resp[6:].decode("utf-8", "ignore"))
s.close()
PY
adb forward --remove tcp:19001
```

通过标准：

- `sle_data_app` 返回 `raw ST forwarded`。
- `sle_data_app` 日志出现 `[CMD][ST-RX] root_id=101 dst_node_id=109 st_len=21`。
- `sle_data_app` 日志出现 `[CMD][ST-TX] ... ret=0`。
- COM 脚本解析到目标 ST，且 Modbus RTU CRC 正确。

  - 当前协议已收敛为 `0x05/0x06/0x02`，拓扑为 69 个 DTU 和 9 个外接设备；旧版结果只保留为链路压力参考，不作为当前协议验收依据。
- relay-open raw ST：
  - ST：旧版 padded relay ST，仅保留为历史记录。
  - `sle_data_app` 回包：`raw ST forwarded`。
  - 板端日志：`[CMD][ST-TX] root_id=1 dst_node_id=1 ... len=26 ret=0`。
  - COM 侧可捕获：`modbus_rtu=010500000000CDCA`、`crc_ok=true`。
- relay-close raw ST：
  - ST：旧版 padded relay ST，仅保留为历史记录。
  - `sle_data_app` 回包：`raw ST forwarded`。
  - 板端日志：`[CMD][ST-TX] root_id=1 dst_node_id=1 ... len=26 ret=0`。
  - COM 侧可捕获：`modbus_rtu=01050000FF008C3A`、`crc_ok=true`。

结论：

- 旧版 23/26 字节 relay ST 记录只作为历史现象保留；当前协议下 DATA payload 不再允许 padding，因为 payload 即完整 Modbus RTU。

当前判断：

- 网关侧封包、命令 IPC、`sle_data_app` raw ST 转发和 SLE write confirm 已通过。
- 当前协议规定 IPC `root_id` 选择 SLE root 连接，ST `dst_node_id` 指向目标 DTU，root 固件按目标节点自动转发。
- 当前协议下不再做 ST payload padding。

下一步建议：

- root 固件在业务解析前增加 raw ST 下行打印，格式使用纯十六进制或 `ST` 原始帧，避免只打印部分业务类型。
- 若 root 固件支持业务 ACK，后续把 ACK 经 SLE notify 回传，作为比 COM 打印更稳定的下行验收依据。
