# 上下行测试包格式与用例

本文记录当前 Gateway 真实 SLE 联调使用的上行、下行测试包格式和验收用例。协议封装职责固定在 `gatewayd`：物模型、Modbus RTU 和 ST DATA 帧都由 `gatewayd` 构造；`sle_data_app` 只管理 SLE 连接，并把 IPC 收到的 raw ST 原样写入 root。

## 1. 总体链路

上行链路：

```text
Windows COM 脚本
  -> DTU root UART
  -> SLE notify
  -> sle_data_app notify_printer
  -> gatewayd SLE data IPC
  -> Modbus 解析
  -> ThingsKit MQTT/SQLite
```

下行链路：

```text
ThingsKit/本地测试命令
  -> gatewayd command
  -> gatewayd 构造 Modbus RTU
  -> gatewayd 构造完整 ST DATA
  -> sle_data_app raw ST forward
  -> SLE write root
  -> DTU root COM 打印或业务处理
```

## 2. ST DATA 帧格式

当前 ST 帧头长度固定为 13 字节，小端字段如下：

| 偏移 | 长度 | 字段 | 示例 | 说明 |
| --- | ---: | --- | --- | --- |
| 0 | 2 | magic | `53 54` | ASCII `ST` |
| 2 | 1 | version | `01` | 当前版本 |
| 3 | 1 | frame_type | `02` | DATA；`01` 为 HEARTBEAT |
| 4 | 1 | src_role | `01`/`04` | root 上行为 `01`，gateway 下行为 `04` |
| 5 | 2 | src_node_id | `01 00` / `00 00` | 上行 root 为 1，下行 gateway 为 0 |
| 7 | 2 | dst_node_id | `00 00` / `01 00` | 上行发 gateway 为 0；下行发 root 为 1 |
| 9 | 2 | seq | `2A 00` | 测试序号 |
| 11 | 2 | payload_len | `0A 00` | payload 字节数 |
| 13 | N | payload | 见下文 | `modbus_type + modbus_len + modbus_rtu` |

payload 格式：

| 偏移 | 长度 | 字段 | 说明 |
| --- | ---: | --- | --- |
| 0 | 1 | modbus_type | `2=meter`，`3=env_sensor`，`4=relay` |
| 1 | 1 | modbus_len | 后续 Modbus RTU 字节数 |
| 2 | N | modbus_rtu | 标准 Modbus RTU，末尾 CRC16-Modbus 小端 |

## 3. 上行测试包

脚本位置：

```bash
app/Gateway/sle_data_app/test/dtu_root_run_sender.py
```

Windows 执行使用 `py -3`，串口固定 115200 8N1。打开串口会导致 DTU 初始化，因此脚本先持续发送 warmup 文本，再发送 ST 帧。

单 root、`METER_001` 上行示例：

```bash
py -3 dtu_root_run_sender.py COM19 COM23 COM36 \
  --scenario meter-001 \
  --duration 60 \
  --interval 1 \
  --line-delay 0.02 \
  --warmup-sec 5 \
  --warmup-interval 0.2 \
  --warmup-text 12123213 \
  --post-warmup-delay 3 \
  --no-heartbeat
```

串口写入格式：

```text
0 <ST_FRAME_HEX>\r\n
```

`0` 表示目标 gateway 节点，`ST_FRAME_HEX` 为完整 ST DATA 帧十六进制文本。

`METER_001` dry-run 样例：

```text
0 535401020101000000020017000215010410089B023004D103C3138800018ABA00005D95
```

拆解：

| 字段 | 值 |
| --- | --- |
| ST 头 | `53 54 01 02 01 01 00 00 00 02 00 17 00` |
| payload | `02 15 ...` |
| modbus_type | `02`，单相电表 |
| modbus_len | `15`，21 字节 |
| modbus_rtu | `01 04 10 ... 5D 95` |
| CRC | `95 5D`，小端 |

上行验收日志：

```bash
adb shell "grep -E 'SLE-IPC|telemetry batch|publish success kind=telemetry' /userdata/gateway/data/log/gateway.log | tail -20"
```

通过标准：

- `sle_data_app` 日志出现 `[SLE][RX]` 和 `[SLE][DECODED]`。
- `gatewayd` 日志出现 `SLE-IPC batch collected`。
- `gatewayd` 日志出现 `publish success kind=telemetry`。
- 缓存不持续增长：`telemetry_cache` 计数保持 0 或可恢复补传。

## 4. 下行测试包

下行测试包由 `gatewayd` 构造。当前本地隔离测试可通过 ADB forward 直接连接板端 `sle_data_app` 命令 socket，发送 `CMD_METHOD_RAW_ST_DOWNLINK=100`，用于验证 raw ST 转发和 root COM 打印。

命令 IPC 参数格式：

| 偏移 | 长度 | 字段 | 说明 |
| --- | ---: | --- | --- |
| 0 | 2 | root_id | root 节点 ID，小端 |
| 2 | 2 | dst_node_id | ST 帧中的目标节点，小端 |
| 4 | 2 | st_frame_len | ST 帧长度，小端 |
| 6 | N | st_frame | 完整 ST DATA 帧 |

### 4.1 Meter 拉闸

Modbus RTU：

```text
01 10 00 10 00 01 02 AA AA 5A 1F
```

含义：

| 字段 | 值 |
| --- | --- |
| slave_addr | `01` |
| function | `10`，写多个寄存器 |
| register | `0010` |
| value | `AAAA`，拉闸 |
| CRC | `1F5A`，线缆发送顺序 `5A 1F` |

完整 ST 示例：

```text
53540102040000010000000D00020B01100010000102AAAA5A1F
```

### 4.2 Relay 断开

Modbus RTU：

```text
01 05 00 00 00 00 CD CA
```

完整 ST 示例：

```text
5354010204000001002A000A000408010500000000CDCA
```

含义：

| 字段 | 值 |
| --- | --- |
| modbus_type | `04`，继电器 |
| function | `05`，写单线圈 |
| coil | `0000`，默认 channel 0 |
| value | `0000`，断开 |
| CRC | `CACD`，线缆发送顺序 `CD CA` |

### 4.3 Relay 闭合

Modbus RTU：

```text
01 05 00 00 FF 00 8C 3A
```

完整 ST 示例：

```text
5354010204000001002B000A00040801050000FF008C3A
```

含义：

| 字段 | 值 |
| --- | --- |
| modbus_type | `04`，继电器 |
| function | `05`，写单线圈 |
| coil | `0000`，默认 channel 0 |
| value | `FF00`，闭合 |
| CRC | `3A8C`，线缆发送顺序 `8C 3A` |

## 5. 下行验证命令

监听 COM 下行：

```bash
py -3 dtu_downlink_command_tester.py COM19 COM23 COM36 \
  --expect relay-open \
  --expect-root-id 1 \
  --channel 0 \
  --duration 60
```

或在发送上行的同时监听下行：

```bash
py -3 dtu_root_run_sender.py COM19 COM23 COM36 \
  --scenario meter-001 \
  --duration 20 \
  --interval 1 \
  --line-delay 0.02 \
  --warmup-sec 5 \
  --warmup-interval 0.2 \
  --warmup-text 12123213 \
  --post-warmup-delay 3 \
  --hold-open 40 \
  --no-heartbeat \
  --expect-downlink relay-open \
  --expect-dtu-id 1 \
  --expect-channel 0 \
  --stop-on-downlink-match
```

发送 raw ST 到板端命令 socket：

```bash
adb forward tcp:19001 localabstract:/var/run/gateway/sle_cmd.sock
python3 - <<'PY'
import socket, struct
st = bytes.fromhex("5354010204000001002A000A000408010500000000CDCA")
param = struct.pack("<HHH", 1, 1, len(st)) + st
body = bytes([1]) + struct.pack("<H", 0x5101) + bytes([10, 100]) + struct.pack("<H", len(param)) + param
packet = struct.pack("<H", len(body)) + body
s = socket.create_connection(("127.0.0.1", 19001), timeout=5)
s.sendall(packet)
hdr = s.recv(2)
ln = hdr[0] | (hdr[1] << 8)
resp = b""
while len(resp) < ln:
    resp += s.recv(ln - len(resp))
print(resp[6:].decode("utf-8", "ignore"))
s.close()
PY
adb forward --remove tcp:19001
```

通过标准：

- `sle_data_app` 返回 `raw ST forwarded`。
- `sle_data_app` 日志出现 `[CMD][ST-RX] root_id=1 dst_node_id=1 st_len=23`。
- `sle_data_app` 日志出现 `[CMD][ST-TX] ... ret=0`。
- COM 脚本解析到目标 ST，且 Modbus RTU CRC 正确。

## 6. 当前实测结论

测试时间：2026-06-16。

已确认：

- `gatewayd`/`sle_data_app` 最新二进制已推送到板端。
- `test-real-listen` 启动成功，MQTT 已连接。
- COM19、COM23、COM36 均可发送 root 上行，`gatewayd` 能收到 `METER_001` 并上云。
- `METER_001` 30 秒基线：
  - COM19、COM23、COM36 各发送 30 帧，`write_errors=0`。
  - `sle_data_app` 出现 `[SLE][RX]` 和 `[SLE][DECODED]`。
  - `gatewayd` 出现 `SLE-IPC batch collected 4/10/11/10/15/16/8 devices`。
  - MQTT 出现 `publish success kind=telemetry`。
  - `telemetry_cache` 计数为 0。
- `topology-all` 60 秒压测：
  - COM19、COM23、COM36 各发送 11 轮，每口 462 帧，`write_errors=0`。
  - 每口覆盖 31 个 DTU 节点和 11 个外设：`METER_001..METER_007`、`ENV_001..ENV_002`、`RELAY_001..RELAY_002`。
  - `gatewayd` 出现 64/62/126 设备批次，批次 ID 覆盖 DTU、meter、env、relay。
  - MQTT 持续 `publish success kind=telemetry`，最大 payload 约 6626 bytes。
  - `cloud_connected=1`，`telemetry_cache` 计数为 0。
- relay-open raw ST：
  - ST：`5354010204000001002A000A000408010500000000CDCA`
  - `sle_data_app` 回包：`raw ST forwarded`。
  - 板端日志：`[CMD][ST-TX] root_id=1 dst_node_id=1 ... len=23 ret=0`。
- relay-close raw ST：
  - ST：`5354010204000001002B000A00040801050000FF008C3A`
  - `sle_data_app` 回包：`raw ST forwarded`。
  - 板端日志：`[CMD][ST-TX] root_id=1 dst_node_id=1 ... len=23 ret=0`。

未通过：

- COM19、COM23、COM36 均未捕获到 relay-open/relay-close 的完整下行 ST，`downlink_frames_seen=0`。
- 反证测试：将同一 relay-open ST 的 `dst_node_id` 改为 `10` 后，`sle_data_app` 仍返回 `raw ST forwarded`，日志出现 `[CMD][ST-TX] root_id=1 dst_node_id=10 ... ret=0`，COM 侧仍未捕获到完整下行 ST。

当前判断：

- 网关侧封包、命令 IPC、`sle_data_app` raw ST 转发和 SLE write confirm 已通过。
- 现有 `sle_gateway_protocol.md` 规定下行 ST `dst_node_id` 指向目标 Root，Root 内部再路由到 DTU；因此 gatewayd 当前 builder 保持 `root_id` 选择 SLE 连接、ST `dst_node_id=root_id` 的设计。
- 端到端“COM 打印完整下行包”未通过，问题更可能在 root 固件的下行接收打印路径或业务过滤路径。

下一步建议：

- root 固件在业务解析前增加 raw ST 下行打印，格式使用纯十六进制或 `ST` 原始帧，避免只打印部分业务类型。
- 若 root 固件支持业务 ACK，后续把 ACK 经 SLE notify 回传，作为比 COM 打印更稳定的下行验收依据。
