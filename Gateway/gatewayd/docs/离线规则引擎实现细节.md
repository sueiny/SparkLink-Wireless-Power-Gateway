# 离线规则引擎实现细节

> Status: Current implementation reference.
> Authority: `gatewayd` 离线规则引擎边界、配置、状态机和本地控制链路以本文为入口。
> Superseded by: None.
> Last verified against: doc status reviewed on 2026-06-28; recheck `src/rules` before rule-engine code changes.

本文说明 `gatewayd` 当前离线规则引擎的实现边界、配置方式、规则状态机、事件输出和本地下行控制链路。规则引擎只在断网或云不可达时运行，联网时不触发本地规则和本地控制。

## 1. 定位

离线规则引擎用于网关断网运行期间的确定性保护和本地告警。它和本地 AI 的边界不同：

- 规则引擎：阈值明确、结果可解释，可触发本地下行控制。
- 本地 AI：趋势风险评分，只产生 `ai_risk` 事件，不直接控制设备。

当前实现遵循 `gatewayd` 高内聚边界：

- `gatewayd` 负责物模型、规则、命令、Modbus 和 ST 下行封装。
- `sle_data_app` 只负责 SLE 连接管理、上行 IPC 转发、下行原始 ST 写入 SLE。
- 规则引擎不解析 SLE/ST/Modbus 原始帧，只消费标准化 `TelemetryData`。

## 2. 模块边界

核心类：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| `gateway::rules::OfflineRuleEngine` | `include/rules/offline_rule_engine.h`、`src/rules/offline_rule_engine.cpp` | 纯计算：输入遥测批次，输出规则事件和离线控制动作。 |
| `PublishManager` | `src/app/publish_manager.cpp` | 离线门控、事件入发布队列、控制动作入命令队列。 |
| `CommandManager` / `CommandExecutor` | `src/command` | 复用现有命令校验、设备路由和下行执行链路。 |
| `SleDownlinkBuilder` | `src/codec/sle_downlink_builder.cpp` | 在 gatewayd 内构造完整 ST 下行帧。 |
| `ConfigManager` | `src/config/config_manager.cpp` | 读取并校验阈值、覆盖项和离线控制配置。 |

`OfflineRuleEngine` 不访问 MQTT、不写 SQLite、不发送 IPC，也不阻塞 SLE 或命令线程。

## 3. 离线门控

离线门控由 `PublishManager::offlineAnalysisActive()` 统一维护。原始离线条件为：

- 网络不可用。
- 云端 TCP 探测不可达。
- MQTT 未连接。

原始离线持续超过 `offline_analysis.enter_hold_ms` 后，规则引擎启用。恢复后按 `offline_analysis.exit_hold_ms` 保持一段时间再退出，避免网络抖动导致反复触发。

在线或未进入离线门控时，`OfflineRuleEngine::evaluate(..., offline_state=false, ...)` 会清空状态，不产生事件和控制动作。

## 4. 配置入口

规则相关配置位于 `gateway_config.json` 的 `offline_analysis`：

```json
"offline_analysis": {
  "enable": true,
  "offline_only": true,
  "enter_hold_ms": 10000,
  "exit_hold_ms": 30000,
  "rule_engine": {
    "enable": true,
    "cooldown_ms": 60000,
    "defaults": {
      "single_phase_meter": {
        "nominal_voltage_v": 220.0,
        "over_voltage_v": 235.4,
        "under_voltage_v": 198.0,
        "frequency_low_hz": 49.8,
        "frequency_high_hz": 50.2,
        "rated_current_a": 60.0,
        "over_current_ratio": 1.1,
        "hold_ms": 10000
      },
      "env_sensor": {
        "high_temperature_c": 55.0,
        "high_humidity_rh": 90.0,
        "hold_ms": 30000
      },
      "dtu_node": {
        "offline_timeout_ms": 60000
      }
    },
    "device_overrides": {
      "METER_001": {
        "rated_current_a": 80.0,
        "over_current_ratio": 1.2
      }
    }
  },
  "offline_control": {
    "enable": true,
    "offline_only": true,
    "relay_close_on_recovery": true,
    "relay_devices": ["RELAY_001"]
  }
}
```

配置优先级：

```text
device_overrides > 设备类型 defaults > 代码内默认值
```

`device_overrides` 使用 0 作为未覆盖哨兵值；只写需要覆盖的字段即可。

## 5. 配置校验

`ConfigManager::validate()` 当前会校验：

- `offline_analysis.offline_only` 必须为 true。
- `enter_hold_ms`、`exit_hold_ms` 必须为正数。
- `rule_engine.cooldown_ms` 必须为正数。
- 电表、电压、频率、电流阈值必须为正数。
- 欠压阈值必须低于过压阈值。
- 频率下限必须低于频率上限。
- 温湿度阈值和 hold 时间必须为正数。
- DTU 离线超时必须为正数。
- `offline_control.offline_only` 必须为 true。
- `relay_devices` 必须存在于设备配置里，且类型必须是 `relay_device`。
- `device_overrides` 只能引用已配置设备，覆盖后的上下限仍必须合法。

因此当前规则引擎阈值已经支持直接在 `gateway_config.json` 中配置，不需要重新编译。

## 6. 当前规则

| 设备类型 | 规则 ID | 触发条件 | 严重度 | 控制动作 |
| --- | --- | --- | --- | --- |
| `single_phase_meter` | `over_voltage` | `voltage > over_voltage_v` 持续 `hold_ms` | `warning` | 无 |
| `single_phase_meter` | `under_voltage` | `voltage < under_voltage_v` 持续 `hold_ms` | `warning` | 无 |
| `single_phase_meter` | `frequency_deviation` | 频率低于下限或高于上限持续 `hold_ms` | `warning` | 无 |
| `single_phase_meter` | `over_current` | `current > rated_current_a * over_current_ratio` 持续 `hold_ms` | `critical` | 电表拉闸，联动 relay 断开 |
| `env_sensor` | `high_temperature` | `temperature >= high_temperature_c` 持续 `hold_ms` | `warning` | 无 |
| `env_sensor` | `high_humidity` | `humidity >= high_humidity_rh` 持续 `hold_ms` | `warning` | 无 |
| `dtu_node` | `node_offline` | 设备超过 `offline_timeout_ms` 未出现 | `warning` | 无 |

过流恢复时，如果 `offline_control.relay_close_on_recovery=true`，会联动配置的 relay 闭合。电表当前只自动拉闸，不自动合闸，避免恢复供电风险。

## 7. 状态机

每条规则按 `device_id:rule_id` 维护状态：

| 字段 | 说明 |
| --- | --- |
| `condition_since_ms` | 异常条件开始持续的时间。 |
| `normal_since_ms` | 规则激活后恢复正常的开始时间。 |
| `last_event_ms` | 上一次事件时间，用于冷却。 |
| `active` | 当前规则是否处于激活态。 |

触发逻辑：

1. 异常条件为 false 时，如果规则已经激活，则等待正常状态持续 `exit_hold_ms` 后清除。
2. 异常条件首次为 true 时记录 `condition_since_ms`。
3. 异常持续达到 `hold_ms`，且距离上次事件超过 `rule_engine.cooldown_ms` 后，产生事件。
4. 事件产生后规则进入 active，重复异常不会在冷却期内重复上报。

## 8. 事件输出

规则事件通过 `PublishManager::enqueueRuleEvents()` 进入统一发布队列：

- topic：`cloud_client_.eventsTopic()`
- kind：`PublishMessageKind::RuleEvent`
- event：规则 ID，例如 `over_current`

事件 details 示例：

```json
{
  "rule_id": "over_current",
  "source": "offline_rule_engine",
  "offline": true,
  "value": 96.8,
  "threshold": 96.0,
  "unit": "A",
  "duration_ms": 10000,
  "rated_current_a": 80.0,
  "over_current_ratio": 1.2
}
```

MQTT 离线时，规则事件和普通遥测一样进入 SQLite 缓存；联网恢复后由发布线程补传。

## 9. 本地控制链路

过流规则触发后，规则引擎输出 `OfflineControlAction`，不直接发 IPC。后续链路：

```text
OfflineRuleEngine
  -> PublishManager::enqueueOfflineControlActions()
  -> command_queue_ local_only RawCommandMessage
  -> CommandManager
  -> CommandValidator
  -> CommandExecutor
  -> gatewayd 内部构造 Modbus + ST 下行帧
  -> IpcCmdSender
  -> sle_data_app 原始 ST 转发
  -> DTU root
```

控制动作仍复用 `set_relay` 命令语义：

- 电表拉闸：目标设备为异常电表，`state=0`。
- relay 断开：目标设备为 `offline_control.relay_devices` 内的 relay，`state=0`。
- relay 恢复闭合：异常恢复且 `relay_close_on_recovery=true` 时，`state=1`。

具体 Modbus 和 ST 帧格式见 `云到DTU上下行链路与包格式.md` 与 `上下行测试包格式与用例.md`。

## 11. 验证方式

构建：

```bash
cd app/Gateway
bash .claude/skills/run-gateway/driver.sh build-gw
```

配置验证：

- 把任一阈值改成负数，确认 gatewayd 启动失败且错误明确。
- 把欠压阈值改到高于过压阈值，确认配置校验失败。
- 把 `relay_devices` 改成不存在的设备或非 relay 设备，确认配置校验失败。

功能验证：

- 在线状态下注入异常遥测，确认不触发本地规则。
- 离线超过 `enter_hold_ms` 后注入过流，确认产生 `over_current` 事件和本地控制动作。
- 监听 `sle_data_app` 日志，确认只出现 raw ST 转发，不出现 meter/relay 业务解析。
- COM 侧确认 DTU root 收到 gatewayd 封装好的完整 ST 下行帧。
