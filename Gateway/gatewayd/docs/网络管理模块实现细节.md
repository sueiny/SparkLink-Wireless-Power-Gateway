# 网络管理模块实现细节

> Status: Current implementation reference.
> Authority: `gatewayd` 网络管理模块、Provider、路由/DNS 和 MQTT 连接关系以本文为入口。
> Superseded by: None.
> Last verified against: `gatewayd/config/gateway_config.json` network block on 2026-06-28.

本文说明 `gatewayd` 当前网络管理模块的实现方式、运行链路、关键边界和已落地稳定性处理。网络模块的目标不是直接发送 MQTT，而是持续维护一个可用的 `NetworkState`，让发布线程在正确的网络条件下连接 ThingsKit MQTT。

## 1. 模块边界

网络管理相关代码集中在：

| 文件 | 职责 |
|------|------|
| `include/app/network_worker.h`、`src/app/network_worker.cpp` | 独立网络线程，按 `retry_delay_ms` 退避调用 `NetManager::ensureNetwork()`，保存最近一次网络状态。 |
| `include/network/net_manager.h`、`src/network/net_manager.cpp` | 网络选择器，按 `network.mode` 和 `priority` 选择 provider，维护当前选中接口。 |
| `include/network/i_network_provider.h`、`src/network/i_network_provider.cpp` | provider 抽象接口，定义 `bringUp()`、接口状态、IP、云端连通性检测。 |
| `ethernet_provider.*` | 以太网拉起和 DHCP。 |
| `wifi_provider.*` | Wi-Fi 配置生成、`wpa_supplicant` 启动、DHCP。 |
| `cellular_provider.*` | 4G provider 框架，当前只检测候选接口，未实现拨号拉起。 |
| `network_utils.*` | Linux 网络工具函数：接口 UP、IPv4 检测、TCP 探测、子进程执行、DHCP 请求。 |
| `netlink_utils.*` | 默认路由读取、删除和添加。 |
| `src/app/publish_manager.cpp` | 读取 `NetworkWorker` 状态，在发布前确保 MQTT 已连接。 |
| `src/cloud/mqtt_cloud_client.cpp` | MQTT client，只负责 libmosquitto 连接、订阅、发布和回调状态。 |

当前边界是：

- `NetManager` 负责选网、拉起网络、默认路由和云端 TCP 探测。
- `PublishManager` 负责根据网络状态连接 MQTT、订阅命令 topic、发布 telemetry/status。
- `MqttCloudClient` 不修改系统网络，只调用 libmosquitto。

## 2. 配置入口

配置来自 `gatewayd/config/gateway_config.json` 的 `network` 字段：

```json
{
  "network": {
    "mode": "auto",
    "cloud_test_host": "thingskit.aiotcomm.com.cn",
    "cloud_test_port": 11883,
    "priority": ["ethernet", "wifi", "cellular"],
    "ethernet": {"enable": true, "ifname": "eth1"},
    "wifi": {"enable": true, "ifname": "wlan0", "ssid": "...", "password": "...", "country": "CN"},
    "cellular": {"enable": true, "ifname": "ppp0"}
  }
}
```

解析逻辑在 `ConfigManager::load()`：

- `network.mode` 支持 `auto`、`ethernet`、`wifi`、`cellular`。
- `priority` 决定候选 provider 顺序，数值越小优先级越高。
- `cloud_test_host` 和 `cloud_test_port` 用于 `canReachCloud()`，默认可回落到 ThingsKit MQTT host/port。
- `mode=auto` 现在是抢占式优先级：高优先级接口一旦恢复可上云，会在下一次网络检查周期内抢占当前低优先级链路。
- `mode=ethernet|wifi|cellular` 保持固定模式：只检查指定 provider，不会跨 provider 抢占。

## 3. 运行线程

`NetworkWorker::run()` 是网络状态刷新入口：

```text
NetworkWorker::run()
  while !stop:
    state = NetManager::ensureNetwork()
    保存 state
    sleep retry_delay_ms
```

这里独立成线程的原因是 `ensureNetwork()` 可能执行：

- `wpa_supplicant` 启动或状态查询。
- DHCP 请求。
- DNS 解析和 TCP 连接探测。
- 默认路由修正。

这些操作可能阻塞数秒，因此不能放在 MQTT 发布热路径里直接执行。

## 4. NetworkState

`NetworkState` 是发布线程能看到的网络快照：

```cpp
struct NetworkState {
    NetworkType type = NetworkType::None;
    std::string name = "none";
    std::string ifname = "none";
    bool cloud_reachable = false;
    bool available = false;
};
```

字段含义：

- `available=true`：接口存在、UP、有有效 IPv4；即使云暂时不可达，这个值也可以保持为 `true`。
- `cloud_reachable=true`：通过当前默认路由和 DNS，能 TCP 连到 `cloud_test_host:cloud_test_port`。
- `ifname`：当前选中接口，例如 `wlan0`。

注意：`available=true` 不等于 MQTT 已连接。MQTT 是否连接由 `MqttCloudClient::isConnected()` 单独维护，并体现在 `cloud_connected` 上报字段里。

## 5. NetManager 选网流程

`NetManager::ensureNetwork()` 现在分成两条明确路径。

固定模式：

```text
mode in {ethernet,wifi,cellular}
  -> 只找该 mode 对应 provider
  -> 当前就是该接口时走轻量检查
  -> 否则允许 bringUp()
  -> 修正默认路由 + DNS
  -> 成功则返回
```

自动模式：

```text
mode == auto
  -> 当前接口仍健康时，先修正当前接口 route + DNS
  -> 再探测所有更高优先级 provider
  -> 只要更高优先级 provider 满足:
       interface up + IPv4 + DHCP lease + route 对齐 + DNS 对齐 + canReachCloud()
     就在本轮完成抢占
  -> 如果更高优先级探测失败，恢复当前接口 route + DNS
  -> 当前接口失效时，再按 priority 从高到低重新选择
```

关键设计点：

- 固定模式不参与抢占，保证指定网络模式语义不变。
- 自动模式是抢占式优先级，不再是“当前接口健康就一直粘住”。
- 已选中网络时，只有需要重连或抢占检查时才执行 `bringUp()`。
- 高优先级探测失败后，必须把当前业务接口的默认路由和 `/etc/resolv.conf` 恢复回来。

## 6. Provider 行为

### 6.1 EthernetProvider

以太网逻辑较简单：

```text
setInterfaceUp(ifname)
requestDhcp(ifname, 10000)
```

检测时复用默认逻辑：

- `interfaceIsUp()`
- `interfaceHasIpv4()`
- `tcpConnect(host, port)`

### 6.2 WifiProvider

Wi-Fi `bringUp()` 当前流程：

```text
如果 wpa_cli/iw 已连接目标 SSID 且 wlan0 有有效 IPv4:
  直接返回成功，不 flush IP，不重启 DHCP/Wi-Fi
setInterfaceUp(wlan0)
write /tmp/gateway_wpa_wlan0.conf
ip addr flush dev wlan0
wpa_cli -i wlan0 terminate
rm -f /var/run/wpa_supplicant/wlan0
wpa_supplicant -B -i wlan0 -c /tmp/gateway_wpa_wlan0.conf
wait wpa_state=COMPLETED 或 iw link Connected
requestDhcp(wlan0, 15000)
```

当前流程仍能从未知状态强制拉起 Wi-Fi，但已先做幂等复用判断：

- 已连目标 SSID 且有 IPv4 时，不再 flush IP、重启 `wpa_supplicant` 或重启 DHCP。
- 不再执行全局 `killall udhcpc`，避免误伤其它接口 DHCP。
- 不在 `WifiProvider` 中直接删除 eth0/eth2 默认路由，默认路由统一交给 `NetManager`/`netlink_utils` 修正。
- 只有需要重连时才执行 `wpa_cli -i wlan0 terminate` 和后续拉起流程。
- DHCP 或 `dhcpcd` 更新 `/etc/resolv.conf` 是异步的，Wi-Fi 获得 IP 后 DNS 可能还没稳定。

### 6.3 CellularProvider

当前 4G provider 还未实现拨号：

- `bringUp()` 直接返回 `false`。
- `ifname()` 会从配置接口、`ppp0`、`usb0`、`wwan0` 中选第一个存在的接口。
- 如果外部系统已经拨号并提供接口/IP，它可以被检测到；但 gatewayd 自己不会发起 AT/PPP。

## 7. DHCP 与 DNS

`requestDhcp()` 的流程：

```text
如果接口已有有效 IPv4:
  return true
如果 dhcpcd 正在运行:
  dhcpcd -m <metric> ifname
  dhcpcd -n ifname
否则:
  udhcpc -i ifname -n -q
等待接口获得非 169.254/16 IPv4
```

这里优先复用系统已有的 `dhcpcd`，只针对目标接口续租；未检测到 `dhcpcd` 时才回退到 `udhcpc`。

`interfaceHasIpv4()` 会跳过 `169.254.0.0/16`，避免把链路本地地址误认为可上云地址。

当前 DNS 不再只“读取全局 `/etc/resolv.conf` 然后碰运气”，而是增加了接口对齐步骤：

```text
readInterfaceLeaseInfo(ifname)
  -> 优先 dhcpcd -U ifname
  -> 提取 gateway / domain_name_servers
  -> 若 nameserver 缺失，回退用 gateway 作为 DNS

reconcileInterfaceNetwork(ifname)
  -> setDefaultRouteVia(ifname, metric)
  -> 若当前路由表中没有该接口默认路由，则回退用 lease gateway 直接重建
  -> 校验 defaultRouteActiveOn()
  -> 检查 /etc/resolv.conf 是否与该接口 nameserver 一致
  -> 不一致则重写 /etc/resolv.conf
```

DNS 探测仍在 `tcpConnect()` 中完成：

- 先检查 `/etc/resolv.conf` 是否存在 `nameserver`。
- 最多等待 15 秒。
- 然后调用 `getaddrinfo()` 解析 `cloud_test_host`。
- 再用非阻塞 socket + `poll()` 做 TCP 连接。

这里的约束已经变成：

1. DNS 仍是全局文件，但内容必须由当前业务接口主导。
2. `/etc/resolv.conf` 不再允许保留多接口混合 nameserver。
3. 如果 route 已切到目标接口，但 DNS 不能对齐，该接口本轮不能被判定为可上云。

## 8. Netlink 路由管理

当前默认路由修正分两步：

- 优先调用 `setDefaultRouteVia(ifname, metric)` 复用系统当前该接口默认路由信息。
- 如果当前路由表里没有该接口默认路由，但 lease 已给出 gateway，则直接用 lease gateway 重建目标默认路由。

实现步骤：

```text
优先从 /proc/net/route 复用目标 ifname 当前网关
如缺失则回退到该接口 DHCP lease 中的 gateway
添加/修正目标 ifname 默认路由
删除其它默认路由
metric 按 provider 固定：eth=100, wifi=200, cellular=300
```

实现细节：

- 默认路由读取使用 `/proc/net/route`，比完整 Netlink dump 简单。
- 添加默认路由使用 `RTM_NEWROUTE` 和 Netlink。
- 删除其它默认路由目前会调用 `ip route del`，因为 dhcpcd 生成的 route 可能带有额外属性，纯 Netlink 精确删除不稳定。
- 跨接口默认路由清理集中在 `netlink_utils`，provider 不直接操作其它接口路由。

已知边界：

- 如果目标接口拿不到 lease/gateway，默认路由和 DNS 对齐都会失败。
- `dhcpcd` 后续续租仍可能改写 route/DNS，所以 `NetworkWorker` 需要周期性修正它们。

## 9. MQTT 与网络状态关系

发布线程使用网络状态的方式：

```text
PublishManager::publishMessage()
  state = network_worker_.state()
  如果 !available 或 !cloud_reachable:
    publish skipped
  ensureCloudConnected()
  publishRaw()
```

`ensureCloudConnected()` 现在做四件事：

1. 如果已连接但 `network_ifname` 变化，先主动断开旧 MQTT 连接。
2. 如果 MQTT 已连接，补确认命令 topic 是否订阅。
3. 如果未连接，读取当前 `NetworkState` 并执行 `reconcileInterfaceNetwork(ns.ifname)`。
4. 在 route + DNS 对齐后，再调用 `MqttCloudClient::connect()`。

当前需要明确的限制：

- `MqttCloudClient::setBindInterface()` 仍主要用于记录期望接口和诊断。
- libmosquitto 真实出口仍依赖系统默认路由和全局 DNS，所以必须先做 route + DNS 对齐。
- MQTT 切网靠“主动断开 + 按新接口重连”来保证一致性。

因此日志里的 `connecting ..., expected_ifname=wlan0` 表示“按网络状态期望走 wlan0”，不表示 MQTT socket 已经强制绑定 wlan0。

## 10. 当前现场状态样例

当前板端稳定状态应满足：

```text
default via 192.168.50.1 dev wlan0 metric 200
wlan0 inet 192.168.50.56/24
cloud_connected=1
network_ifname=wlan0
network_type=wifi
# /etc/resolv.conf
nameserver 192.168.50.1
```

如果其它系统进程后续又改写了 `/etc/resolv.conf` 或默认路由，`NetworkWorker` 会在下一次检查周期按当前业务接口重写回来。

## 11. 常见问题定位

### 11.1 Wi-Fi 已连但 MQTT 失败

检查：

```bash
adb shell "ip route"
adb shell "ip -4 addr show wlan0"
adb shell "cat /etc/resolv.conf"
adb shell "grep -E 'NET|MQTT|cloud_connected|wlan0|DNS|connect' /userdata/gateway/data/log/gateway.log | tail -120"
```

判断：

- 如果默认路由不是 `wlan0`，看 `setDefaultRouteVia()` 是否失败。
- 如果默认路由是 `wlan0` 但 DNS 指向其它网段，优先看是否出现 `dns mismatch` / `dns realigned` 日志。
- 如果 `cloud_reachable=false`，发布线程会跳过 MQTT publish。
- 如果 `cloud_reachable=true` 但 MQTT connect timeout，重点看 broker DNS、TCP 端口和 libmosquitto 回调。

### 11.2 DHCP 重置导致短时断网

检查日志：

```bash
adb shell "grep -E 'bringUp|wpa_supplicant|udhcpc|has no IPv4|transient failure|fixed mode|preempt selected' /userdata/gateway/data/log/gateway.log | tail -120"
```

判断：

- 只要进入 Wi-Fi `bringUp()`，当前实现会 flush IP 并重启 `wpa_supplicant`。
- 正常保活路径不应反复出现 `bringUp`。
- 如果只是云暂时不可达，不应因为 `cloud_reachable=false` 就在下一轮无条件重复 `bringUp()`。

### 11.3 DNS 窗口期失败

检查：

```bash
adb shell "cat /etc/resolv.conf"
adb shell "nslookup thingskit.aiotcomm.com.cn 2>/dev/null || ping -c 1 thingskit.aiotcomm.com.cn"
adb shell "grep -E 'cannot reach cloud|publish skipped|connect failed|connect timeout' /userdata/gateway/data/log/gateway.log | tail -80"
```

判断：

- `tcpConnect()` 已等待最多 15 秒 DNS nameserver 出现，但不能保证 nameserver 可达。
- 如果 nameserver 被其它服务改成了错误接口，下一次检查周期应出现 `dns realigned to <ifname>` 并自动修回。

## 12. 已知风险

| 风险 | 影响 | 当前表现 |
|------|------|----------|
| Wi-Fi 重连仍有破坏性 | 真正需要重连时仍会 flush wlan0 IP 并重启该接口的 wpa_supplicant | 已增加目标 SSID + IPv4 复用判断，正常保活不再重置。 |
| DNS 仍是全局文件 | 其它系统服务仍可能在检查周期之间改写 `/etc/resolv.conf` | 下一轮会输出 `dns mismatch` / `dns realigned` 并修回。 |
| MQTT 未真正绑定接口 | `expected_ifname=wlan0` 只是日志语义 | 依赖默认路由正确性。 |
| 目标接口没有 lease gateway | 既没有当前默认路由，也没有 DHCP lease gateway 时无法重建默认路由 | 会报 `ROUTE_DRIFT` 或 `no gateway for <ifname>`。 |
| Cellular 未实现拨号 | `cellular` 不能作为独立兜底链路 | 只有外部已拨号时才可能检测到。 |
| 失败状态粒度仍偏粗 | `available/cloud_reachable` 尚未拆成完整状态机 | 当前已输出 DNS、路由、TCP 原因，便于现场排障。 |

## 13. 已落地稳定性处理

### 13.1 Wi-Fi 和 DNS 稳定性处理

- `WifiProvider::bringUp()` 先判断目标 SSID + 有效 IPv4，满足时直接复用当前 Wi-Fi。
- 移除全局 `killall udhcpc` 和 `killall wpa_supplicant`，重连时只对目标 `wlan0` 执行 `wpa_cli terminate`。
- `NetManager` 对当前接口 link/IP 检测增加连续失败阈值，短暂抖动不会立刻释放当前 Wi-Fi。
- `NetManager` 在固定模式和自动模式的保活检查中，都会先修正当前接口 route + DNS，再判断能否真正上云。
- `mode=auto` 已改成抢占式优先级，高优先级链路恢复后会在下一检查周期完成抢占。
- `canReachCloud()` 失败时输出 TCP/DNS 原因、默认路由摘要和首个 nameserver。
- 默认路由先按现有路由修正，必要时再用 DHCP lease gateway 重建，避免“有 IP 但无默认路由”时无法抢占。
- `/etc/resolv.conf` 只保留当前业务接口 nameserver，不再混合多接口 DNS。
- MQTT 在接口切换时会主动断开并按新接口重连，避免 network state 已切换但 MQTT 还挂在旧链路。
- MQTT 连接日志使用 `expected_ifname=...`，避免误判为真实 socket 绑定。
